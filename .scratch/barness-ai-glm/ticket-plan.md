## 共同行为与实施纪律

- 三协议复用现有 adapter 与公共 Client E2E；两目标型号、六个 Model 身份都在范围。
- 每票先写所覆盖的失败场景与公共 E2E，再实现；完工留下可重放请求、事件、Result、Attempt/Usage、断言与脱敏审计。发现回归时在该票内修复，不拖到最终门禁。
- 每个功能票在自己的协议上完成模型/请求/流/结果/测试闭环。01 是必要且有界的前置重构，独立以既有路线行为不变验收，不是未完成的新基础框架。
- 现有模块允许 01 原子迁移并保持绿色，无需 expand–contract；遵守删除旧内部路径、无 shim/双写的项目原则。
- 02 只把共享 Provider/候选 Host 装配和 Chat 文本跑通。04、06 不等待 03；新协议不继承 Chat 的能力事实。
- 每条路线的基础/增强票分别拥有自己最小失败、usage presence、callback 和资源验收；08、09 验证组合差异和跨路线行为，不是推迟这些测试的理由。
- 06 的实际契约核查与 07 的高级未知字段探针使用现有公共 Client 和有界候选入口。11 汇总完整六组合验收，不能成为前面建探针能力的反向依赖。
- 候选报告与正式目录报告区分；真实预算严格沿用 spec，缺 Key 为 NOT_RUN。正式条目与支持矩阵只在来源和证据齐备后纳入。
- 12 同票迁移正式目录、矩阵、路线注册和十三组合结构校验，不把校验器更新推给 13；13 负责完整当前证据、Host 文档与回滚，不补先前票未实现的生产行为。
- 每次 shared adapter 变更都跑受影响原厂/DeepSeek 回归；10 给出最终固定基线/扩展结论。13 不承担为之前未完成的能力补实现。

## 拟议切片

1. **[01：拆分厂商协议能力并保持既有调用行为](issues/01-provider-capability-prefactor.md)**
   - 阻塞：无。
   - 交付：在准备接入第二个兼容厂商时，Host 对现有 OpenAI、DeepSeek 和 Anthropic 的请求、流、结果与费用行为保持一致；后续 GLM 可以独立选择协议能力，不会被迫继承原厂默认。

2. **[02：通过公共 Client 完成 GLM Chat 文本与思考调用](issues/02-glm-chat-text.md)**
   - 阻塞：01。
   - 交付：Host 使用独立的 zhipu Chat Binding 和候选 Catalog，通过 full/simple 的流式与完整结果入口调用 GLM-5.3、GLM-5.2，并得到正确归属的文本和思考结果。

3. **[03：完成 GLM Chat 工具流与交错思考往返](issues/03-glm-chat-tool-round-trip.md)**
   - 阻塞：02。
   - 交付：Host 收到完整且可逐步观察的 GLM 函数调用，执行工具后将同 turn 推理和工具结果回传，模型继续回答；未接入的工具选择和保留式思考请求得到明确错误。

4. **[04：接通 GLM Responses 并修复对象型内容丢失](issues/04-glm-responses-text-shapes.md)**
   - 阻塞：02。
   - 交付：Host 使用独立的 GLM Responses Binding 获得完整文本和思考；GLM 的单对象或数组 content、只有 done 的结果与无 [DONE] 流都被正确呈现。

5. **[05：完成 GLM Responses 无状态工具往返与缓存提示](issues/05-glm-responses-history-tools-cache.md)**
   - 阻塞：04。
   - 交付：Host 以完整历史完成 GLM Responses 函数工具往返，并安全使用按租户和账户隔离的缓存路由提示；未接入的服务端能力在发送前明确拒绝。

6. **[06：建立 GLM Messages 实际契约并完成文本调用](issues/06-glm-messages-text-contract.md)**
   - 阻塞：02。
   - 交付：Host 使用自己的 GLM Messages Binding，通过公共 Client 收到两个型号的文本结果；请求仅携带本协议已证实的字段，GLM-5.3 不被默认关闭思考。

7. **[07：完成 GLM Messages 工具、思考与原生续接](issues/07-glm-messages-tools-thinking-replay.md)**
   - 阻塞：06。
   - 交付：Host 接收 GLM Messages 的函数调用和可用思考块，执行工具后继续生成；签名、无签名 thinking 和工具结果都按 GLM 真实规则往返。

8. **[08：让三协议的失败、重试和用量可解释](issues/08-glm-failures-retry-usage.md)**
   - 阻塞：04、06。
   - 交付：Host 在 GLM 认证、额度、暂时限流、断流或取消时得到准确错误和已知用量；显式重试只用于可恢复的初始请求，缺失用量不会被当成免费。

9. **[09：验证共享 Client 的隔离、回调授权与资源释放](issues/09-glm-isolation-resource-callbacks.md)**
   - 阻塞：03、05、07、08。
   - 交付：本地与云端 Host 共享 Client 并发使用三种 GLM 协议时，租户、账户、原生状态和缓存互不串用；回调不能越权，取消和限额会及时释放资源。

10. **[10：固定 GLM 的 pi 差分与扩展边界](issues/10-glm-pi-differential.md)**
   - 阻塞：09。
   - 交付：维护者能从冻结 pi 基线和公共请求/结果证据判断每条 GLM 路线的兼容范围，明确区分真实差分通过与基线没有路由的扩展。

11. **[11：取得六个候选型号组合的真实 API 与价格证据](issues/11-glm-candidate-live-evidence.md)**
   - 阻塞：09。
   - 交付：维护者通过公共 Client，在三种 GLM 官方协议上分别验证 GLM-5.3 和 GLM-5.2 的必交能力，并获得可追溯的容量、用量和美元价格候选快照。

12. **[12：发布六个正式目录条目与三个独立支持记录](issues/12-glm-formal-catalog-support-matrix.md)**
   - 阻塞：10、11。
   - 交付：Host 能从内置 Catalog 查询两型号各自的三协议身份与正确美元价格；支持矩阵只显示这三条 GLM 路线在正式目录快照下取得的自身证据。

13. **[13：完成 Host 接入、十三组合发布门禁与回滚证明](issues/13-glm-release-host-docs-rollback.md)**
   - 阻塞：12。
   - 交付：Host 可依据完整示例配置三份 GLM Binding，维护者能用当前完整证据作出可发布判断，并在需要时禁用 GLM 或恢复上一完整版本。
