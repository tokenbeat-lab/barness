# barness 模型目录维护与本地加载

Status: resolved
Updated: 2026-11-01

本文最初根据已确认的设计、讨论、来源研究与 ADR-0058 生成；当时仅生成规范。现已完成本期实现与普通验收，当前结果见 [唯一当前状态](status.md)。Status 不表示线上发布或完整人工阶段通过。

## Problem Statement

barness 的模型目录同时服务本地和云端 Host。现有型号、能力、调用约束和价格由程序中的目录定义提供；沿用既有协议的新型号也需要修改目录代码，维护者难以通过一次可审查的数据变更完成新增、改价、下架与恢复。

models.dev 能提供主要模型资料，但其 serving offering、canonical 资料、默认 API、推理选项和价格条件与 barness 的语义不同。直接导入会混淆地区 Provider、操作和协议，把缺失费率变成免费，或用其他服务方、其他操作的价格覆盖已经确认的定义。维护者需要保留字段归属、人工判断和可重放的来源。

目录变更还缺少统一的预览、确认、候选检查、应用与历史闭环。JSON 可解析不能证明当前代码遵守模型硬约束；检查通过后重新映射、修改版本或应用变化后的基准，也会使实际生效内容脱离受测内容。

Host 需要加载本地目录，并分清当前程序接受了哪些模型、哪些模型不可用及其原因。单条模型的新字段或无效定义不应阻断其他有效模型；损坏的完整文件也不能通过静默剔除或回退被掩盖。目录收录、代码接受、厂商实测及租户授权必须继续分别表达。

## Solution

建立由 barness 审核维护、按 Provider 管理的唯一目录维护源。以 models.dev 指定端点为主要输入，用公共字段规则、Provider 对照、逐四维身份的来源关联和人工补充完成转换；官方资料与 barness 历史证据用于补缺和处理冲突。

提供供维护者及外部 AI 调用的确定性 CLI。所有实际变更先预览并显式确认，冻结包含拟生效版本的 Catalog Candidate，再通过当前实际代码的受控 E2E，最后应用同一候选。失败保留候选和证据，既有生效目录不变。Provider 内容版本、变更原因和历史可查询，回退通过新变更恢复旧内容。

从同一维护源生成内置默认 JSON 与外部本地 JSON。独立目录组件在 Host 装配时校验完整文件，再逐模型严格加载，返回 Effective Catalog 与全部 Model Load Status。Host 仍通过现有 Config.Catalog 构造 Client，并通过独立报告展示不可用原因。Client、模型查询、Binding 授权和固定价格快照继续沿用现有契约。

本期交付维护 CLI、候选受控检查及本地 JSON 加载。运行时不联网更新目录；不维护模型最低软件版本，不承诺旧程序兼容，也不以受控检查宣称真实厂商支持。

## User Stories

1. As a 目录维护者, I want 使用 models.dev 的指定目录作为主要输入, so that 新型号和价格变化可以被集中发现与整理。
2. As a 目录维护者, I want 冻结实际使用的来源字节、URL、时间和摘要, so that 后续可以重放本次映射而不依赖变化后的上游。
3. As a 目录维护者, I want 以实际服务方的 offering 关联型号, so that 不会借用 canonical 或其他托管商的路由与价格。
4. As a 目录维护者, I want 显式映射 Provider 别名并保留中国站与国际站的独立身份, so that 地区服务的定义与价格不会互相覆盖。
5. As a 模型接入开发者, I want 按操作、Provider、API 和 ID 确定完整身份, so that 同名模型可以在不同操作和协议中独立维护。
6. As a 目录维护者, I want 一个 offering 只能经明确确认关联多个 API 条目, so that SDK 名称或默认 API 不会隐式扩大目录。
7. As a 目录维护者, I want 公共字段规则集中处理直接转换, so that 不必为每个型号重复维护整份映射表。
8. As a 目录维护者, I want 缺失、有损及 barness 特有字段列为确认项, so that 未证实的推理、能力和价格语义不会直接生效。
9. As a 目录维护者, I want 官方文档、公告、模型 API 和历史证据补充来源缺口, so that 上游不完整时仍能保留 barness 的维护判断。
10. As a 目录维护者, I want 来源冲突及人工覆盖记录理由和字段归属, so that 后续刷新不会抹去已经确认的决定。
11. As a 目录维护者, I want 无 type、未支持类型或未映射模态得到明确提示, so that 音频等记录不会被误接纳为聊天模型。
12. As a barness 维护者, I want 初次迁移保留现有 118 条定义和可达行为, so that 改变维护方式不会顺带改变已有型号、价格或缺省语义。
13. As a 目录维护者, I want 准确来源缺失的图片和分类记录保留历史依据, so that 不会用同名聊天或其他服务方资料补造映射。
14. As a CLI 使用者, I want 每个变更入口提供 help 和 dry-run, so that 执行前可以查看计划且不改变维护库或证据目录。
15. As a 外部 AI 调用方, I want 非交互确认和机器可读 JSON, so that 自动化可以按明确状态驱动流程而不猜测自由文本。
16. As a CLI 使用者, I want 错误有稳定类别和非零退出, so that 可以区分定义问题、代码缺口及执行失败。
17. As a 目录维护者, I want 新增模型先产生候选且不隐式覆盖已有身份, so that 每项新增和协议变化都可审查。
18. As a 目录维护者, I want 候选在检查前固定基准、最终内容及拟生效版本, so that 检查覆盖的就是将要应用的目录。
19. As a 目录维护者, I want 区分未确认、待检查、检查失败和可应用候选, so that 不会把未完成工作当作接纳通过。
20. As a 目录维护者, I want check 不改变生效目录并保留失败原件, so that 失败能够复核且不会损坏已有可用目录。
21. As a 模型接入开发者, I want 为每个完整身份执行适用的公共调用合约, so that 新型号的接纳依据包含实际协议与计价行为。
22. As a barness 维护者, I want 缺合约、缺场景、零匹配及执行失败均拒绝接纳, so that 父测试通过或自报 PASS 不能冒充完整覆盖。
23. As a 模型接入开发者, I want 代码缺口与候选关联并在适配后重新检查, so that 新约束不会在未经验证时进入生效目录。
24. As a 目录维护者, I want 无需代码变更即可通过的候选能只通过数据维护完成本地接纳, so that 既有协议的新型号不必增加逐型号代码分支。
25. As a CLI 使用者, I want apply 核对原候选、基准及实际受测输入, so that 内容或代码变化后不能沿用失效检查。
26. As a CLI 使用者, I want apply 应用已检查内容且不重新获取或映射来源, so that 生效字节与检查对象一致。
27. As a 目录维护者, I want 写入失败时不留下半份可用快照或覆盖历史, so that 维护失败后仍能使用原生效目录。
28. As a 目录维护者, I want 每个 Provider 独立维护内容版本, so that 一家的变更无需推进其他家的版本。
29. As a 目录维护者, I want 无变化、预览、查询和失败不推进生效版本, so that 版本只标识实际生效内容。
30. As a Host 开发者, I want 相同 Provider 组成确定相同合成目录身份, so that 无需另行维护人工全局版本。
31. As a 目录维护者, I want 查询每项生效变更的原因、来源、决定和检查证据, so that 可以解释某个字段何时及为何改变。
32. As a 目录维护者, I want 批量更新仅改变语义和单位一致的来源管理价格, so that 改价不会顺带改动能力或协议。
33. As a 目录维护者, I want 批量改价保留人工覆盖并展示上游差异, so that 自动维护不会替我撤销人工判断。
34. As a 成本管理开发者, I want 价格缺失、明确零值及无法表达的条件分别处理, so that 未知费率不会被当成免费或普通基础价。
35. As a 成本管理开发者, I want 上下文阶梯、缓存与图片费率经过独立确认, so that token、模态和按张计价不会混用。
36. As a 目录维护者, I want 上游 missing 或 deprecated 只生成审查提示, so that 账户列表变化不会自动删除现有模型。
37. As a 目录维护者, I want 显式下架指定身份并保留维护记录, so that 下一份快照停止提供该型号且原因可追溯。
38. As a 目录维护者, I want 恢复型号时形成新候选并重新检查, so that 旧记录不会直接跳过当前接纳条件。
39. As a 目录维护者, I want 通过新版本变更回退到旧内容, so that 恢复行为可审查且不改写历史版本或 pin。
40. As a barness 维护者, I want 默认目录与外部本地目录来自同一维护源, so that 不必维护 Go 字面量和 JSON 两套事实。
41. As a Host 开发者, I want 继续使用 BuiltinCatalog 和显式 Catalog 注入, so that 现有装配方式和公开模型类型可以延续。
42. As a Host 开发者, I want 默认目录及查询结果保持独立副本, so that 修改返回值不会影响其他 Client 或在途调用。

## Implementation Decisions

### 1. 职责与依赖

- 唯一维护源按 Provider 管理来源、关联、人工字段、生命周期、版本、候选与历史。维护 CLI 负责映射、预览、确认、检查、应用和查询；CLI 不嵌入 LLM，由外部 AI 或维护者调用。
- 独立目录组件负责本地文件完整性校验、逐模型加载、有效目录装配及报告。barness-ai 继续拥有模型约束、协议能力、请求转换、授权、调用生命周期及计价；Host 选择来源、消费报告并装配 Client。
- 运行依赖保持 Host → 目录组件 → ai；ai 不反向依赖目录组件。目录组件留在根 Go 模块，不引入独立软件版本体系。
- 上游资料、维护模型、运行模型及加载报告独立转换。来源、确认、检查与历史不进入 Model、ImageModel、ClassifierModel 或调用类型；报告不反写运行 JSON。
- 维护工具不以 ai 的内部 testkit 为生产依赖。受控检查通过公共 Client、CLI/进程边界及已有验证工具执行。
- 复用已有依赖与明确职责；不建立通用映射框架、动态 adapter 插件或第二套协议能力表。实现按职责拆分，单文件不超过 500 行。

### 2. 来源与映射

- 主要源为 models.dev 的 catalog.json?type=all 端点，按其 v1 兼容投影解释，不直接套用 v2 TOML schema。实际取回的数据必须固定为可重放输入；记录真实 URL、抓取时间、响应或实际摘录摘要。没有上游整体版本或部署提交时不补造。
- serving offering 是映射主记录；canonical 资料仅作明确关联和通用补充。不能跨服务方、地区或操作借用路由与价格。官方文档、公告、模型 API 及自身历史证据用于补缺和核对冲突，冲突须有明确决定和理由。
- 采用四层维护：公共字段规则、Provider 对照、逐条来源关联、人工补充与覆盖。规则保留修订身份；每个完整模型身份保留源 Provider、源 model ID、可选 canonical ID 及来源摘要。
- 型号身份保持 (Operation, Provider, API, ID)。moonshotai、moonshotai-cn、zhipuai 分别关联 moonshot、moonshot-cn、zhipu；其他关系按实际来源明确配置，不按品牌合并。一个 offering 可以关联多个已确认的 API 条目，不能从 SDK 包名自动展开。
- 本期操作只有 chat、image、classifier；源 decision 经确认对应 classifier。缺省 type 只产生 chat 候选，因为兼容投影可能包含旧音频记录。其他未实现类型报告未支持，不塞入现有操作；未映射模态不得静默丢弃后接纳。
- ID 保留服务方 wire 身份。名称及 reasoning 等直接字段经校验转换；context 与 output 限额须为可表示整数，不能截断小数、用 input 限额替代 context，或补造默认限制。字段只进入有相应语义的目标类型。
- 推理选项、默认档位、compat 与协议接线必须确认。源 effort 的 null 不等于目标 thinkingLevelMap 的“不支持”；tool_call 或 structured_output 不推导 strict mode，temperature 不作为所有 adapter 的通用约束。
- 源 npm、API 基址、shape、body、headers、env 和实验模式仅是维护参考，不自动安装 SDK、启用请求覆盖或进入 Binding、凭据配置。v1 的默认 API 不能证明全部协议组合。
- 人工值及覆盖有字段归属和理由。刷新只生成差异，不覆盖人工值；明确改变人工决定时重新确认。缺失、有损、冲突及必需确认项均须能被机器识别。

### 3. 初次迁移与默认数据

- 初迁移以现有 2026-10-29.1 快照为语义基准，保留 112 条 chat、3 条 image、3 条 classifier，共 118 条记录及其三集合、协议、价格、缺省/显式 null 和可达行为。不得把记录数当作去重型号数。
- 上游关联只补充维护资料并产生待审查差异，不直接用实时响应重建覆盖。聊天的 Provider+ID 命中不证明 API/能力全覆盖；6 条图片和分类记录缺少准确 serving 来源时保留原定义与历史依据，不伪造关联或借价。
- 新的 Provider 版本与合成版本按新规则产生；不把新内容冒充旧版本或旧哈希。历史快照、历史测量及 pin 保留原字节与身份。
- 内置默认 JSON 和外部本地 JSON 从同一维护源确定性生成。以生成数据替换旧内部目录字面量，删除过时人工维护路径，不保留双写、兼容 shim 或两套事实源。
- 保留 BuiltinCatalog() 的公开入口及独立副本行为；ai 使用同源生成数据提供默认目录，不为此反向导入目录组件。Config.Catalog、显式 Catalog 注入、现有模型类型和查询接口继续有效；直接 NewClient 不隐式联网。

### 4. CLI 对外行为

- 命令能力包括按源 Provider/model 新增候选、批量改价、显式下架、恢复、check、apply、版本查询、历史与回退。命令精确拼写由实施确定，行为不能缺失。
- 每个变更入口提供 help、dry-run、JSON 输出及显式确认文件或参数，并支持非交互执行。help、查询和 dry-run 不写维护库或证据目录；实际检查的证据输出位置显式指定且可追溯。
- 输出区分自动映射、缺失、有损转换、人工确认、冲突、拟改内容及必需测试。错误有稳定结构化类别和明确非零退出；查询数据与实际副作用分开表达。
- 新增入口列出目标操作/API 与 barness 特有字段的确认项。已有完整身份不得隐式覆盖；新增协议条目需明确确认。来源不可取得、映射冲突或确认不足时，不产生生效目录。

### 5. 候选、检查与应用

- 流程固定为：钉住来源 → 预览差异 → 显式确认 → 冻结候选 → 受控 check → apply 原候选 → 本地生效 JSON 及内置生成数据。新增、改价、能力/确认变更、下架、恢复和回退均走该流程。
- 候选保存基准身份、完整最终内容、拟生效版本、差异、确认项及检查证据引用。候选未确认、待检查、检查失败及可应用状态必须可区分；检查失败进一步区分定义问题、代码缺口和测试/执行失败。
- check 覆盖最终内容及版本，仅测试当前选定的实际代码。每个完整身份须有适用合约和实际场景；缺合约、缺场景、零匹配、非零退出或执行未完成均不能成为通过。结论统一称为“代码兼容通过”。
- 检查记录受测提交、实际源码与输入摘要、候选摘要、执行入口、场景集合、命令、真实退出和原件引用。不能仅凭调用者填写的 PASS、顶层测试 PASS 或 JSON 能解析决定可应用。
- apply 必须核验候选、基准与所需实际受测输入仍匹配，并确认检查确实完成。基准、候选或受测实现变化后，拒绝沿用失效计划；重新形成适用候选并检查，不自动合并。
- apply 仅写入已经检查的内容，不重新抓取来源、重算映射或改变已检查版本/字节。失败保留候选与证据，既有生效目录不受影响。
- 文件写入采用满足该本地流程的原子保存方式，保存失败不得留下半份可用快照或虚报成功；候选和历史不覆盖既有原件。实际生效写入有变更记录，不因失败抹去历史。
- 无需改代码即可受控通过的候选可完成本地数据接纳；存在代码缺口时保留候选并关联适配变更，适配后重验。未来独立发布或软件配套发布的动作均不在本期执行。

### 6. 版本与变更追溯

- 每个 Provider 独立内容版本。冻结候选时先确定拟生效版本，成功 apply 后才推进；查询、预览、无变化或失败不推进生效版本。同一已生效版本不能对应不同内容。
- 按 Provider ID 稳定排序组合各 Provider 的选定版本与内容摘要，自动产生单份 Catalog.Version。不增加人工全局版本；相同组成和输入生成相同输出，生成时间等非语义值不进入确定性内容。
- 变更记录包含操作、范围、原因、来源/规则身份、显式决定、基准与结果摘要以及检查证据。历史追加，不改旧版本、不删除失败记录；内容版本不能由上游型号日期替代。
- 回退是恢复旧内容的新变更，保留当前完整接纳流程并产生新的生效版本，不重写旧版本、旧 pin 或旧检查结果。
- 不维护模型最低软件版本、schema 代次、兼容协商或旧版本矩阵。受测代码身份用于追溯本次证据，不作运行时过滤或历史兼容承诺。

### 7. 价格与生命周期

- token 基础价格按 USD/百万 token 确认输入、输出、缓存读及缓存写四项。维护边界检查字段是否实际提供，普通 float64 零值不能证明来源已提供费率；明确零价及免费项保留确认依据。
- 批量改价只对来源管理且单位、计费条件一致的字段生成候选；人工覆盖保留并提示差异。来源缺价时保留已有值并提示待确认，新增必需值不足则阻止接纳，不补零。
- 阶梯需确认完整费率及严格大于边界；barness 沿用整请求换价。不能从投影后的 size 推断原 gt/gte，也不能把 context_over_200k 别名当作固定 200000 门槛或重复应用。
- 图片参数、每模态费率和每图价格独立确认。token 输出价不转成每张价；缓存 TTL、地区、服务等级或其他无法对应的条件须补充确认或代码适配，不能悄悄压成普通费率。
- cost update 仅改变价格，不顺带刷新协议和能力。价格及估算继续遵守现有 Usage、Estimated Cost 与 Price Snapshot 契约。
- 上游 missing、deprecated、账户列表变化或未来停服日期仅形成审查提示。下架须显式指定完整身份、范围和原因，从下一份生效快照移除，维护源和历史保留。
- 恢复形成新候选并重新检查。加载所选快照时不叠加内置旧条目，已下架或未加载型号不会被补回；请求不可用型号明确报错，不自动替代。

### 8. 本地文件与逐模型加载

- 运行文件沿用外层 hash、catalog；catalog 保持 version、models、imageModels、classifierModels 的已有形状与省略语义。来源、确认、检查、历史及内存加载报告不加入运行文件。本地格式不预先决定未来线上发布格式。
- Host 明确选择内置或外部本地文件。加载先严格检查完整 JSON、根结构、已知顶层字段、版本及集合形状；保留原始模型 JSON，不先把所有模型解码成 typed Catalog。
- 在模型语义解析前，以完整原始 catalog 的紧凑 JSON 校验外层 hash。紧凑只去除字符串外 JSON 空白，不重排属性、不改数字或转义；未知模型字段也参与来源完整性校验。该步骤不调用整目录语义校验。
- 随后为每条记录提取完整或部分身份、所属集合与数组位置，再逐条严格解码和校验。未知模型结构字段、字段类型/值错误及可明确识别的当前不支持协议/能力只影响该条；原始失败定义和原因保留，不能去掉未知字段后当作成功。
- 对可识别的完整四维身份检查重复；同组所有条目均失败，不择第一条或最后一条。身份不完整或非模型对象按位置保留失败记录，不能冒充可用完整身份。
- 对成功候选复用 ai 的模型约束和实际协议能力依据。单条临时 Catalog 的 Hash 可复用部分校验，但不能代替通用身份完整性、路由接纳或重复组检查；不复制另一套协议表。
- 只将成功条目按来源集合及原顺序装配为有效 ai.Catalog，保持缺省语义，重新计算有效 Hash，并返回全部条目的报告。失败条目不会进入 Lookup、ModelsOf 或公共调用索引。
- JSON 无法解析、顶层结构/字段/集合形状错误或来源摘要不符时拒绝整份文件，返回文件级原因，不通过过滤模型挽救完整性错误，也不静默改选其他来源。Host 可以在知道失败后显式选择内置目录，此选择不属于加载器自动回退。
- 单模型失败不是整个加载调用的致命错误。零成功时仍返回完整报告与空有效集合，供 Host 展示无可用模型原因；不能把全部失败伪装成正常提供模型。

### 9. 报告、摘要与固定快照

- 报告是独立内存结果，包含来源版本、来源摘要、有效摘要、成功/失败数量，以及各条完整或部分身份、集合/位置、状态、诊断与建议。失败原始条目可供可信 Host 诊断，不自动写日志、对外响应或混入模型调用。
- 状态为 loaded 或 failed。失败原因至少区分 unknown_field、unsupported_definition、invalid_definition 和 duplicate_identity；文件失败另给文件级原因。诊断保留足够定位上下文，公开展示继续遵守既有归属与脱敏边界。
- loaded 仅表示当前程序接受了定义，不表示厂商实测通过、服务健康或 Binding 已授权。未知字段/明确不支持项可建议检查目录或尝试升级；无效定义应提示修复，不能把任意错误归因于版本过旧或猜测最低可用版本。
- 来源响应/摘录摘要用于维护重放；外层 hash 标识完整原始 catalog；Catalog.Version 保留来源已确定的内容/合成版本；Catalog.Hash 标识当前接受的 typed 目录及其版本。这些身份分别记录，不互相替代。
- 过滤后的有效摘要允许不同于外层摘要；相同来源因程序接受集合不同，也可能得到不同有效摘要。禁止以过滤后 Hash 校验完整输入，或用来源摘要冒充实际计价集合。既有 Catalog.Hash 算法不变，CallMetadata 继续使用有效 Version/Hash。
- Host 装配后目录及加载状态固定。更改文件、加载报告或公开查询副本不能改变当前 Client；在途调用及所有重试固定原目录和价格快照，不在调用时重新解释文件。
- 运行时认证、限流、网络和厂商参数错误仍按既有调用结果/错误返回，不反写加载状态，不新增自动下架、恢复、重试、切模型、切协议、切 Provider 或目录回滚。已配置的 Binding 重试策略继续遵守原契约。

### 10. 接纳与权限边界

- Provider 保证既有协议向后兼容是设计前提，不证明新增必需参数、特殊请求行为或新计费语义已被代码实现。现有 Kimi、xAI 及图片/分类的固定型号约束须逐项按实际能力和受控场景评估；不能笼统删除限制或凭 JSON 解码放行。
- 目录发现、维护接纳、模型加载成功、厂商实测和租户授权保持独立。新增定义不改变 Binding 白名单、凭据解析、账户作用域或跨操作授权；拒绝仍发生在对应原有边界。
- 本期 check 不调用真实模型 API，不持有真实厂商凭据，不更新真实支持资格。受控结果不能改写历史支持矩阵、测量时间、授权或发布通过结论。

## Testing Decisions

### 公共测试边界与实施顺序

- 以“维护 CLI/子进程 → 候选/check/apply → 本地 JSON → 目录组件公共加载入口 → 现有公共 Client”为主要 E2E 链路。复用现有受控 Provider、协议夹具与验证工具，不为映射函数或内部存储增加测试专用生产接口。
- 加载损坏或不支持的定义无法通过正常接纳流程生成，因此在目录组件公共加载入口直接提供固定本地文件，再检查报告、公共查询和可用模型调用；这与主链路共用 Host 装配和 Client 边界。
- 好的测试验证使用者可观察的退出、JSON、文件副作用、版本/摘要、加载状态、请求/响应、用量和授权行为，不绑定私有函数、内部文件拆法或对象布局。不能仅由待测目录生成所有预期；关键 wire、价格边界及迁移基准来自独立夹具。
- 先列失败方式并在上述公共边界建立失败场景、保留原件，再写实现；不得实现后补写单元测试。确需隔离测试时，先完整列出失败方式并说明公共 E2E 无法覆盖的原因。
- 测试边界沿用已确认设计中的受控加载、CLI/进程及公共调用方向，具体执行遵循测试 SOP。此处定义计划，不宣称任何新增场景已经运行。

- 使用已有验证工具留存独立 attempt，包含真实 argv、数字退出、受测提交及实际来源/输入摘要、固定上游输入、候选/基准/结果、完整必需场景清单、受控请求/响应、断言、manifest 与脱敏 audit。失败原件不被成功重跑覆盖；重放不得依赖临时目录中的已删除字节。
- 现有验证工具的默认来源覆盖不足以自动包含新增目录组件、维护 CLI、维护数据及规则；这些实际参与检查和 apply 的代码/输入须显式逐文件绑定。摘要有记录但原字节未保留的历史研究不能充当新的可重放输入。
- 普通受控检查不继承真实 key、live、race、压力或冻结 oracle 开关；新 CLI 子进程检查包含文件失败、取消和超时。需要精确退出码的 CLI 验收使用编译后二进制并留存二进制身份，避免包装退出掩盖结果。
- 本期新增接纳门槛只要求代码兼容证据，无真实厂商请求。实施若仅迁移既有定义，沿用真实证据也须说明适用范围；若实际修改协议/生命周期等行为，先离线核对受影响捕获，不能直接宣称原资格自动适用。本规范不授权付费调用，也不绕过 SOP 的后续判定。
- race、压力按实际共享状态、并发路径和资源影响单独选择。有依据的不适用与尚未执行分别记录；适用阶段须按 SOP 等待人类明确选择，文档确认或普通 check 不代替该授权。后续发布门禁另行只读判定，不把 apply 成功写成 release.pass=true。

## Out of Scope

- 线上目录发布、上传、静态托管、DNS/TLS、barness.dev 配置及最终线上发布物格式。
- 运行时直连 models.dev 或 Provider 模型列表、目录下载、网络缓存、latest 入口、启动联网检查、五秒预算及 Provider 网络失败回退。
- 进程中刷新、后台更新、热替换 Client 或自动合并目录；加载器静默选择另一份目录或以默认条目补回失败/下架记录。
- 模型最低软件版本、schema 代次、兼容协商、旧软件版本矩阵及由当前测试推断历史兼容。
- 新模型操作、通用映射/插件框架、自动安装 SDK 或 adapter，以及不由实际候选需要驱动的协议能力扩展。
- CLI 内嵌 LLM、自动接受上游变更、自动覆盖人工定义、缺价补零、按列表缺失/deprecated 自动下架。
- 模型健康探测、运行错误自动改变加载状态、自动切换模型/协议/Provider，或扩展现有 Binding 重试策略。
- 新 Host UI、模型调用权限管理平台、真实厂商测试、正式支持资格晋升及完整发布通过声明。
