# 模型目录维护与本地加载：讨论记录

更新日期：2026-11-01。状态：本轮修订 Q1–Q16 及整体方案已确认，维护者已授权更新设计和相关文档；产品尚未实施。当前唯一设计入口为 [design.md](design.md)，当前架构决策为 [ADR-0058](../../docs/adr/0058-barness-catalog-maintenance-and-isolated-loading.md)。

本文件前半部记录本轮有效决定，后半部完整保留 2026-10-29 的旧讨论。两轮都曾使用 Q 编号：下表的 Q1–Q16 是本轮修订；历史附录的 Q1–Q17 不作为现行指令。models.dev 字段事实与覆盖核对见 [专项研究](models-dev-research.md)，历史 Pi 研究见 [research.md](research.md)。

## 1. 本轮确认的需求与边界

- 主维护源改为 models.dev 指定端点；有对应关系的字段直接转换，barness 特有或缺失/有损字段显式确认。保留自有定义的维护权。
- 引入确定性的维护 CLI 和候选流程；生效前需实际代码上的受控 E2E，所有实际变更可追溯。
- 目录无需代码变更即可通过时，未来可独立发布；代码适配后才通过时，未来代码与目录配套发布。本期仅生成和加载本地 JSON。
- 新版目录不带最低软件版本。加载器逐模型严格处理，不认识或不接受的模型保留失败原因，正常模型仍可用。
- Provider 向后兼容仍为前提；无真实模型 API 测试，不声称厂商实测资格。
- 线上发布、下载、缓存、启动联网预算和最终线上结构退出本期；原本的域名及五秒方案只作历史背景。

## 2. 本轮问答与最终答案

| 问题 | 最终决定 |

| Q2：AI 与 CLI | 外部 AI 调用确定性 CLI；CLI 不内置 LLM，提供 help、dry-run、结构化输出及显式确认路径 |

| Q4：最低版本来源（历史中间选择） | 当时曾选择根 Go 模块的软件版本；随后被 Q6 全面撤销，不是当前实现要求 |
| Q5：候选与生效 | 新增、改价、下架等先成候选，经确认、检查后原子应用；失败保留候选，生效目录不变 |
| Q6：最低版本（用户修订） | 取消最低软件版本与版本过滤；通过测试即可接纳，加载/使用失败保留诊断并适当提示升级。受测代码身份只用于证据 |
| Q7：批量成本更新 | 只自动更新来源管理且语义/单位一致的字段；保留人工覆盖，来源缺失不补零，缺项显式确认；不顺带更新协议/能力 |
| Q8：下架 | 上游缺失或 deprecated 只产生审查差异；显式下架，保留历史；恢复形成新变更并重新检查 |
| Q9：版本与历史 | Provider 独立版本，成功应用推进生效版本；无变化或 dry-run 不升版本；历史追加，回退生成新变更；合成版本不人工维护 |
| Q10：本地文件 | 沿用 `{hash,catalog}`，现有三集合不变；严格检查未知字段；错误作用范围由 Q11/Q14 细化 |
| Q11：逐模型加载（用户修订） | 不采用整份目录因单条错误而初始化失败的建议。逐模型加载，在内存保留所有条目状态，正常模型进入现有 ai.Catalog |
| Q12：测试维护 | 复用协议合约，逐四维身份确认差异；关键预期来自独立夹具；缺场景不通过；候选改变后重新检查，apply 不重新映射 |
| Q13：初始迁移 | 保留当前 118 条定义及协议、价格、缺省/null 语义，来源仅用于关联及候选差异；历史快照和 pin 不改写 |
| Q14：隔离范围 | 模型字段/能力错误只影响单条；身份不完整按位置记录；重复身份全部冲突条目失败；JSON/顶层/摘要错误拒绝整份；零成功返回报告和空集合 |
| Q15：摘要边界 | 外层 hash 校验完整 catalog 紧凑原文；有效 ai.Catalog 重新算 typed Hash；报告保留两者；Version 沿用来源版本，无最低版本门控 |
| Q16：状态与调用 | 加载状态固定于本次启动；认证、限流、网络及厂商错误不改变加载状态，不自动下架或恢复；Host 按原因展示建议 |

### 已明确撤销或延期的提案

- 撤销 Q4 的最低软件版本来源选择，也撤销曾提出的附属最低版本清单和按版本排除模型。
- 撤销 Q11 原建议中“显式外部 JSON 因单模型问题而整体初始化失败”的处理；文件级错误仍失败，不能静默回退掩盖损坏。
- 严格未知字段规则保留，但模型内的未知字段只使该条不可用，原始条目及原因保留，不能丢弃未知约束后继续调用。
- 不以新版程序通过推断旧版兼容，不增加测试所有旧版的矩阵。未来旧程序差异由逐条状态报告和适当升级提示处理。
- 旧版“先纳入生效目录，再在调用时修复代码”被“候选先确认并通过受控 E2E”取代；运行时厂商错误仍可能发生，受控不冒充真实测量。
- 静态分发、下载、缓存、Provider 网络回退和五秒启动预算延期，不带入本期加载器。

## 3. 讨论树已闭合

1. 维护权与来源：barness 维护自有定义，以 models.dev 为主要输入，官方资料和自身证据补缺/核对。
2. 映射：公共规则、地区 Provider 对照、逐条来源关联和人工覆盖；缺失/有损字段待确认。
3. 维护流程：预览 → 确认并冻结候选 → 受控检查 → 应用原候选；失败不污染生效目录。
4. 生命周期与版本：Provider 独立版本，实际变更有历史，缺价不填零，missing/deprecated 不自动删除，回退新建版本。
5. 接纳与适配：当前受测代码上受控通过才接纳，无最低版本或旧版矩阵；需要代码时关联适配及未来配套发布。
6. 加载：完整输入校验 → 单模型严格处理 → 重复组隔离 → 有效集合＋全部状态报告；文件级错误与单条错误分开。
7. 追溯：来源摘要、有效摘要、来源版本及候选/受测代码身份分清，历史事实和 pin 保留。
8. 调用与 Host：既有 ai 接口、授权及固定快照保留；报告独立，升级只是适当建议，不增加健康状态或自动替换。
9. 分期：本期 CLI、本地 JSON、受控 E2E；线上发布和运行时更新以后再设计。

具体目录、函数或命令拼写在以上边界内实施，不是未决的产品分支。术语仅记录概念，字段和行为合同留在设计稿；不因文档确认自动编写测试或产品实现。

## 历史附录：2026-10-29 讨论原文

日期：2026-10-29。阶段：整体共识已确认，研究与讨论完成，设计已定稿；尚未开始实施。

研究报告见 [research.md](research.md)。本文件记录讨论树与用户已经确认的约束；建议不等于决策。

### 已确认的需求与研究假设

- 已有 Provider 发布的新型号，在沿用已实现协议与参数语义时，应能通过目录数据更新获得适配，不要求为每个型号更新程序。
- 本次先假设 Provider 保证既有协议的向后兼容；出现新协议、新参数或新硬约束时，仍允许且需要代码适配。
- barness 需要维护自己的目录定义及其版本、发布和更新流程；职责不要求全部放入 barness-ai。
- 尽量沿用现有 Catalog 定义与调用接口，评估对其他消费者的影响。
- 先完成背景与可行性研究，再讨论设计；本阶段不修改产品代码。

### 已确认的决策

维护者于 2026-10-29 回答“Q1、Q2都采用你的建议，Q3: 可以先不支持进程中更新，先支持启动时更新一次”。

- **Q1：** barness 审核并独立发布自己的目录，外部来源只生成候选变更。
- **Q2：** 型号纳入与自身实测分别记录；Q16 进一步明确，目录收录也不以当前程序已经适配为前提。未适配/未实测不宣称已完成支持，Binding 授权保持独立。
- **Q3：** 首版仅在应用启动时检查更新一次，选定目录后在进程运行期间固定快照；不做后台刷新或热切换。
- **Q4：** 需要独立组件，Host 安装时即有内置默认目录；首次启动也可检查更新。目录组件在启动时装配快照，NewClient 不隐式联网。
- **Q5：** 接受完整快照与外层发布元数据，按 Provider 维护；当时建议只更新已配置 Provider，后由 Q9 放宽为首版全量检查。独立内容版本由 Q10 确认，装配组合身份由 Q15 确认。
- **Q6：** 采纳用户的 KISS 选择，只维护模型目录内容版本，不增加兼容代次、最低程序版本或版本协商。用户对原问题的理解正确：它原本要处理新版定义与旧程序的兼容；新必需行为仍按初始需求进行代码适配。
- **Q7：** 接受有效缓存 → 内置默认目录的失败回退原则，安装时自带的默认定义就是内置基线。
- **Q8：** 目录数据与维护/发布工具同仓库，采用 Git 审核及可重复发布流程。
- **Q9：** 目录组件维护全量 barness 支持的 Provider；Host 决定启动检查范围。用户允许基于 KISS 全量更新，本轮据此选择首版启动检查全量，不按凭据可用性筛选公开目录。
- **Q10：** 各 Provider 独立内容版本、完整快照、独立失败回退；一家更新失败不阻止其他家的成功更新。
- **Q11：** 保留未配置 Provider 的定义；选定新快照完整替换该 Provider 的旧条目，不把新版删除条目从内置补回。若首版全量检查成功，未配置 Provider 的定义也可以更新；未更新时继续使用已有基线/缓存。
- **Q12：** 内置默认目录与在线发布物从同一份 Git 数据生成；程序发版时选定一版作为随附基线，在线目录继续独立发布。
- **Q13：** Provider 官方文档、公告及模型 API 作为事实依据；Pi/models.dev 用于发现与辅助核对，冲突由维护者记录判断后发布。
- **Q14：** 静态 HTTPS 分发，每 Provider 有最新入口和不可变历史文件，域名为 barness.dev；目前只有域名、尚未配置，不代表分发服务已经上线。
- **Q15：** 采纳自动合成目录身份，只为兼容现有 Client 接收单份 Catalog 的入口；Provider 独立版本/发布/回退不变，不增加人工全局版本。
- **Q16：** 不采纳“未适配就拒绝该 Provider 新版”的建议。新版继续更新，让旧程序感知新型号；新协议/参数适配缺口在单型号调用时暴露并修复。未知新增字段随原始快照保留，目录构造不能因此阻断整家；损坏格式和基本身份无效仍按数据错误处理。
- **Q17：** 接受五秒全量检查总预算，但首版不允许 Host 调整；已完成项可采用，超时未完成项回退，下次启动再检查。

第三轮对第二轮 Q5 的更新范围作了放宽：全量维护与全量更新均获允许。“只配置 OpenAI 时不更新 Anthropic”不再是首版硬限制；按 Provider 独立维护/发布的边界不变。

1. **目录发布权（已确认 Q1）**：barness 审核后独立发布。

2. **目录收录与适配（已确认 Q2/Q16）**：新定义继续更新；目录收录、当前程序适配、自身实测分别记录，调用中暴露适配缺口后修复。
   - ADR-0057 已记录对 ADR-0018 的目录纳入前提修订；损坏数据与未知能力分开处理。
   - 目录发现与服务绑定授权是已有独立边界；新增条目不应隐含扩大 Binding 白名单。
3. **更新生效目标（已确认 Q3）**：首版应用启动检查更新一次，进程中不刷新。
   - 决定后讨论：获取与激活的职责、调用快照、失败回退、更新频率与显式锁定。
4. **更新组件与维护流程（已确认 Q4/Q7/Q8/Q17）**：独立组件、安装自带基线、固定五秒启动检查、数据更新失败按家回退、同仓库 Git 维护。

6. **版本复杂度（已确认 Q6）**：仅维护目录内容版本；此前兼容代次建议未采纳，不继续设计该分支。
7. **范围（已确认 Q9）**：全量维护，首版选择全量启动检查；后续无需为本轮额外实现凭据发现。
8. **同源与分发（已确认 Q12–Q14）**：Git 同源生成，以官方文档/公告/模型 API 等核实事实，通过 barness.dev 静态分发；托管配置尚未实施。

### 第一轮：根决策（原问题与建议，答案见上方）

#### Q1：目录发布权

是否采用 barness 自有审核发布，外部来源只生成候选变更？

建议：是。采集可以自动化，客户端消费 barness 发布的定义；不把 Pi 的客户端兼容门槛当作 barness 的兼容证明。

#### Q2：目录纳入与实测承诺

是否允许符合既有实现能力的新型号先进入可调用目录，将该型号自身实测状态单独记录？

建议：是。沿用用户给出的 Provider 向后兼容假设；纳入仍需审核协议、已知硬约束与元数据，未实测不宣称已验证支持。这样不会把目录更新重新绑定到逐型号 live 测量。需要明确修订相关既有支持范围和纳入规则；Binding 授权保持独立。

#### Q3：首版生效目标

首版是否要求长驻进程无需重启即可采用新目录？

建议：是。覆盖用户提出的本地与云端场景；新逻辑调用可采用新快照，在途调用及重试仍固定旧快照。代价是需要设计目录读取与调用固定点，不能仅在启动前增加下载器，也不能反复重建 Client 而忽略资源状态。若用户选择启动/显式重装配时生效，则相应收窄首版范围。

用户采纳 Q1、Q2，Q3 选择首版仅启动时更新。更新组件归属、发布技术、旧版本分发及删除语义仍未决定。

### 第二轮：边界与发布契约（原问题与建议，答案见上方）

#### Q4：更新组件归属

是否由独立目录组件负责获取、缓存和校验，由 Host 在启动时调用，再把选定的现有 Catalog 传给 barness-ai？

建议：是。barness-ai 保持固定快照及现有调用接口；直接调用 NewClient 不隐式联网。具体包路径与公开接口待职责确认后确定。

#### Q5：完整快照与发布元数据

是否每版发布完整目录，发布元数据放在外层，内层沿用现有 Catalog？

建议：是。新版本完整定义该版型号集合，可表达删除；启动选择远程发布版、历史快照或内置基线之一，不把所有来源永久叠加。来源、验证状态与发布信息不塞入现有 Model 等公共类型。删除型号不替代 Binding 授权撤销。

#### Q6：旧程序兼容标识

在尚无 barness-ai 独立产品版本号的情况下，是否先用简单的“目录兼容代次”标识实现要求？

建议：是。程序声明自身实现代次，目录发布物声明所需最低代次；消费者只选择其能理解的发布版。已有实现覆盖的新型号/价格修订只变内容版本；需要新必需行为的定义才要求更高代次。格式版本仍单独描述解析形状。该名称与规则待用户确认，当前未写入术语表。

#### Q7：启动更新失败

启动检查失败、超时或发现不兼容发布版时，是否允许继续采用上次有效且兼容的缓存，没有时采用内置基线？

建议：是。更新等待有界，失败不覆盖有效缓存，并给出明确诊断；允许本次仍使用旧目录。具体时限、显式离线/锁定的例外与首次安装行为待此原则确认后展开。

#### Q8：维护与发布流程

是否先在同一仓库用 Git 维护独立目录数据和发布工具，按“审核提交 → 校验 → 生成不可变发布物 → 发布”形成闭环？

建议：是。先建立可重复的维护与发布命令，再接自动化；部署位置与上传渠道随后确定。该建议不表示当前已有 CI，也不引入新的运营后台。

### 第三轮：Provider 更新范围与版本（原问题与建议，答案见上方）

#### Q9：如何确定更新范围

是否由 Host 显式提供需要更新的 Provider 集合，目录组件不扫描环境凭据或租户密钥？

建议：是。只配置 OpenAI 就只检查 OpenAI，行为由 Host 配置明确决定。Provider 仍遵循已有身份边界，国际站与中国站不因品牌相同合并。

#### Q10：Provider 版本与失败隔离

是否每个 Provider 独立维护目录内容版本、发布完整快照，并在更新失败时只回退该 Provider？

建议：是。例如 OpenAI 有新版可采用，而 Anthropic 更新失败时保留其缓存/内置定义，彼此不阻塞。只维护目录版本，不额外增加程序兼容版本；多份快照合成后如何填写现有 Catalog.Version，待此选择确认后再定。

#### Q11：未更新 Provider 的定义

是否保留未配置 Provider 的内置定义，仅不联网更新；已配置 Provider 则用其选定的完整快照替换该 Provider 的条目？

建议：是。尽量保持现有完整 Catalog 的发现行为；同一 Provider 不把新版与旧版型号永久叠加，因此新快照删除的型号不会由内置目录重新出现。保留目录定义不授予 Binding 调用权限。

用户明确全量维护范围，允许 KISS 全量更新；Q10、Q11 采纳建议。首版选择全量检查，保留全部 Provider 的发现；后续确定合成目录身份、来源与具体发布流程。

### 第四轮：来源与分发（原问题与建议，答案见上方）

#### Q12：单一维护来源

内置默认目录和在线发布物是否从同一份 Git 目录数据生成，程序发版时选取其中一版作为随附基线？

建议：是。在线目录可独立更新，程序发布才更新随附基线；保留 BuiltinCatalog 等既有入口，避免 Go 字面量与在线 JSON 各自手工维护。

#### Q13：目录事实来源

是否以 Provider 官方文档/公告为主要依据，以 Pi/models.dev 为发现线索与辅助来源，冲突由维护者记录判断后发布？

建议：是。自动采集只生成候选变更；协议硬约束、价格和模态等事实仍须按 barness 定义审核，不能按字段外形直接覆盖。

#### Q14：静态发布物分发

首版是否用 HTTPS 静态文件分发，各 Provider 提供最新版本入口及不可变历史文件？

建议：是。发布工具生成可上传文件，目录组件通过可配置的分发地址获取；版本发布不需要运行目录业务服务。具体托管平台/域名仍待部署选定，本问题只确定静态分发契约。
