# barness 模型目录维护与本地加载设计

日期：2026-11-01。状态：设计已确认；维护者已授权更新文档，尚未开始产品实施。

本版取代 2026-10-29 设计中的来源优先级、先收录后适配和首期在线更新范围。当前决策见 [ADR-0058](../../docs/adr/0058-barness-catalog-maintenance-and-isolated-loading.md)，本轮问答及历史取舍见 [discussion.md](discussion.md)。models.dev 的 schema、字段与有损投影见 [专项研究](models-dev-research.md)，Pi 的历史背景见 [research.md](research.md)。

本地事实基线为 `5be6828d13561cf0fee2b7e56f1cd0f9678da7af`；本轮只更新文档，实施前须重新核对实际源码和输入。下文包路径、命令名称及内存字段名为实施提案，职责与行为边界为已确认设计。

## 1. 目标、前提与本期范围

目标是让沿用已实现协议的新模型通过维护数据被接纳，减少逐型号修改目录代码的延迟，同时保留 barness 对协议接线、硬约束、价格与变更的审核责任。

前提：Provider 保证既有协议向后兼容。新协议、必需参数、特殊请求行为或新计费语义仍可能要求代码适配；上游模型记录不能自行安装这些能力。

本期包括：

- 以 models.dev 为主的分层映射、人工确认和按 Provider 管理的唯一维护源。
- 确定性的维护 CLI：候选、检查、应用、版本、批量改价、下架、历史及回退。
- 受控 E2E 的代码兼容接纳门槛及可追溯证据，不调用真实模型 API。
- 内置默认 JSON 和外部本地 JSON 的加载；逐模型隔离，返回有效目录及内存加载报告。
- 保持现有 `ai.Catalog`、`Config.Catalog`、`BuiltinCatalog()`、查询接口、四维身份和固定调用快照。

本期不包括目录线上发布、运行时下载更新、网络缓存、启动联网时间预算、进程中刷新或最终线上发布物格式。`barness.dev` 仍只是已确定且尚未配置的域名。旧版设计中的 `latest.json`、静态 URL、五秒预算及网络失败回退均不作为本期实施合同。

不维护模型最低软件版本，不增加 schema 代次、兼容版本协商或旧软件版本测试矩阵。受测代码身份仍作为证据记录，不用于运行时版本过滤。

## 2. 组件职责、依赖与数据边界

| 部分 | 建议位置 | 职责 |
| --- | --- | --- |
| 唯一维护源 | `catalogs/`，按 Provider 分组 | 钉住上游资料、来源关联、人工补充与覆盖、生命周期、Provider 内容版本、候选和变更记录 |
| 维护 CLI | `tools/catalog/` | 读取来源、映射、展示差异、消费确认、冻结候选、执行受控检查、应用本地快照及查询历史 |
| 独立目录组件 | 根 `catalog/` Go 包 | 严格读取本地 JSON、校验完整输入、逐模型加载、装配有效 `ai.Catalog`、返回全部条目加载报告 |
| barness-ai | 既有 `ai/` 包 | 模型与协议约束、请求/响应转换、授权、固定调用和计价；保留现有公共类型与注入方式 |
| Host | 启动装配及展示边界 | 选择内置或外部本地文件、消费有效目录与报告、构造 Client、展示模型不可用原因与适当升级建议 |

运行时依赖为 Host → catalog → ai；`ai` 不反向导入 `catalog`。目录组件仍在根 Go 模块内，不建立独立软件版本体系。维护工具不以 `ai/internal/testkit` 为生产依赖；受控测试经公共 Client、CLI/进程边界及既有验证工具执行。

维护模型、上游协议资料与运行模型在边界独立转换。来源、确认、验证和操作记录不进入现有 `Model`、`ImageModel`、`ClassifierModel`。加载报告是运行组件的独立返回值，不写入运行目录或模型调用类型。

默认 JSON 与外部本地 JSON 从同一维护源生成。后续实现用生成数据替换旧内部目录字面量，不保留两套人工维护入口或兼容 shim；`BuiltinCatalog()` 继续返回独立副本，直接 `NewClient` 不隐式联网。

## 3. 主源与分层映射

主要输入为 <https://models.dev/catalog.json?type=all>。该端点是上游 v2 资料的 v1 兼容投影，不能按 v2 TOML schema 直接解释。

`providers[provider].models[model]` 表示实际 serving offering，是映射主记录；根 `models[canonicalID]` 表示与托管商无关的模型资料，只用于明确关联与补充。不能因 canonical 同源而借用其他服务方的价格，也不能将同名 chat offering 用作 classifier 依据。

Provider 官方文档、公告、模型 API 资料及 barness 自身历史证据用于补充缺项、核对冲突。列表受账户、区域或分页影响，缺失不构成自动删除。运行时不请求 models.dev 或 Provider 模型列表。

### 3.1 四层映射与字段归属

| 层 | 维护内容 | 约束 |
| --- | --- | --- |
| 公共字段规则 | 同名/同义字段转换、单位与范围检查 | 集中维护，不逐模型复制完整字段表；记录规则修订身份 |
| Provider 对照 | models.dev ID → barness Provider ID | 地区独立；如 `moonshotai` → `moonshot`、`moonshotai-cn` → `moonshot-cn`、`zhipuai` → `zhipu` |
| 条目来源关联 | 每个四维身份对应的源 Provider、源 model ID、可选 canonical ID、来源摘要 | 同一 offering 可关联多个明确确认的 API 条目，不据 SDK 包名自动展开协议 |
| 人工补充与覆盖 | API、硬约束、推理接线、能力与价格差异、确认依据 | 覆盖有归属和理由，后续自动刷新不覆盖人工值 |

完整身份保持 `(Operation, Provider, API, ID)`。本期类型仍为 chat、image、classifier；models.dev `decision` 对应 classifier，其余未实现类型只报告未支持，不扩展业务操作。缺省 `type` 仅生成 chat 候选，不能直接确认，因为 v1 还可能包含无 `type` 的旧音频记录。

### 3.2 主要字段映射与必须确认的差异

| models.dev 字段 | barness 目标 | 映射要求 |
| --- | --- | --- |
| offering `id`、`name` | 各模型 `id`、`name` | ID 保留服务方 wire 身份；Provider、操作和 API 通过显式关系确定 |
| `reasoning` | chat `reasoning` | 布尔事实可映射；不能据此推导所有推理控制参数 |
| `modalities.input/output` | 对应类型的 `input/output` | 仅声明当前程序支持且已确认的能力；不静默丢弃未映射模态 |
| `limit.context` | chat/classifier `contextWindow` | 检查为可表示整数；`limit.input` 没有当前独立目标，不能替代 context |
| `limit.output` | chat `maxTokens` | 不套用于没有该字段的 image/classifier；不截断小数或无条件补默认值 |
| `cost.input/output/cache_read/cache_write` | token 模型四项费率 | 确认同为 USD/百万 token；缺失不同于零，缺项必须确认 |
| `cost.tiers[].tier.size` 及阶梯价格 | `cost.tiers` | 上游投影丢失 `gt/gte` 区别；barness 是严格大于边界且整请求换价，需确认完整四费率及边界 |
| `reasoning_options`、`interleaved` | 推理映射、默认档位、compat/协议接线 | 必须确认；源 effort `null` 的 wire 语义未证实，不等同目标 map 的 `null=不支持` |
| `tool_call`、`structured_output`、`temperature` | 能力确认的参考 | 不直接推导 `supportsStrictMode`；现有 `supportsTemperature` 主要作用于 Messages，不能作为所有 adapter 的通用约束 |
| `provider.npm/api/shape/body/headers` | 协议确认的参考 | 不自动导入 SDK、基址、任意 body/header 或凭据配置；v1 只保留默认 API，不能证明全部 API 组合 |
| image 数据及 v1 token 价格 | image capabilities/pricing | 图片参数、每模态费率、每图价格仍须确认；token output 价不能当作每张图价格 |
| `status`、日期、canonical 资料、实验模式 | 维护资料、候选差异 | 不自动下架，不将来源日期当目录版本，不自动启用实验 body/header |

`context_over_200k` 是兼容别名，不能假定实际门槛为 200000 或与 `tiers` 重复应用。v1 未完整表达的媒体收费、缓存 TTL、地区/服务等级等条件必须显式补充或保持待确认。更完整字段意义和例外见 [models-dev-research.md](models-dev-research.md)。

## 4. 唯一维护源与初次迁移

维护侧逻辑上保存以下信息；物理文件布局在实现时保持简单，不引入通用映射框架：

- 上游实际摘录及其 URL、抓取时间（实际发生时记录）、响应摘要与可重放输入；上游没有整体版本，不伪造部署源码提交。
- 公共映射规则与 Provider 对照，以及逐四维身份的来源关联。
- 人工值、确认/覆盖的字段归属、依据、生命周期及历史快照来源。
- 候选的基准身份、完整目标内容、拟生效版本、差异、确认项和检查证据引用。
- 不可改写的 Provider 历史版本与追加变更记录。

以 [现有快照](../../ai/release/catalog-snapshot.json) `2026-10-29.1` 的 118 条记录为初始语义基准：112 条 chat、3 条 image、3 条 classifier。当前聊天条目可按 Provider+ID 找到来源，不等于 API 全覆盖；另外 6 条没有准确的完整 serving 对应。保留它们的历史依据，不借用同 canonical 或同名 chat 的价格。

初迁移保留协议条目、价格、值、缺省/显式 null 的区别及现有可达行为。来源只建立关联并产生待审查差异，不从实时上游重新生成后直接覆盖。旧快照和 pin 不改写；新的 Provider 版本/合成版本按本设计产生，不能把新内容冒充旧哈希。

## 5. CLI 合同与候选闭环

CLI 由外部 AI 或维护者调用，不嵌入 LLM。命令族示意为 `model add`、`cost update`、`model retire`、`model restore`、`check`、`apply`、`version`、`history`、`rollback`；精确命名在实施时具体化。

所有变更入口提供 help、dry-run、机器可读 JSON、显式确认文件/参数与非交互路径。输出应分清自动映射、缺失、有损转换、人工确认、冲突、拟改内容和必需测试；不依赖 AI 阅读自由文本后猜测状态。错误要有稳定的结构化类别和明确非零退出；查询结果与副作用清楚分开。

`model add` 以源 Provider 和 model 为输入，列出需要确认的目标操作/API及 barness 特有字段。已有四维身份不被隐式覆盖；新增协议条目需要明确确认。来源不可取得、确认不足或映射冲突时不产生生效目录。

```text
钉住来源 → dry-run 差异 → 显式确认 → 冻结候选（含拟生效版本）
         → 受控 check → apply 原候选 → 本地生效 JSON / 内置生成数据
```

候选未确认、待检查、检查失败与可应用状态必须可区分。失败分为定义问题、代码缺口、测试/执行失败；不把任意错误自动判定为需要升级。候选和失败证据保留，已有生效目录不受失败影响。

检查覆盖拟应用的最终内容，包括版本。`apply` 验证候选、基准与受测输入未变，以及所需检查确实完成；不接受仅由调用者填写的 PASS。通过后应用已检查的内容，不重新抓取来源、重算映射或改写已检查字节。基准改变则拒绝原计划，重新形成候选并检查，不自动合并。

实际写入和变更有记录；help、查询和 dry-run 不写维护库或证据目录。检查证据的输出位置须显式、可追溯；检查本身不改生效目录。文件保存失败不能留下半份可用快照，候选/历史记录不覆盖既有原件。

## 6. 版本、改价、下架及回退

每个 Provider 独立内容版本。候选提前确定拟生效版本供检查，成功 apply 才推进生效版本；无变化、失败、查询或预览不升生效版本。同一版本不可对应不同已生效内容。

按 Provider ID 稳定排序组成版本和内容摘要，自动确定合成 `Catalog.Version`，不引入人工全局版本。相同组成与输入产生相同结果；生成时间等非语义运行值不混入确定性内容。模型最低程序版本、schema 代次和兼容协商不进入维护或运行模型。

变更记录覆盖新增、改价、能力/确认更新、下架、恢复和回退，包含操作、范围、原因、来源/规则身份、显式决定、基准/结果摘要及检查证据。历史追加，不改旧版本或抹去失败。回退通过新变更恢复旧内容，仍经过相应确认和检查，不覆盖历史 pin。

### 6.1 批量改价

| 情况 | 行为 |
| --- | --- |
| 来源管理且单位、条件语义一致 | 形成价格候选差异 |
| 人工覆盖 | 保留人工值，提示来源变化待确认 |
| 来源缺失 | 不补零；已有值保留并显式提示待确认，新增必需值不足则阻止接纳 |
| 阶梯、计费单位或价格条件无法对应 | 不自动应用，要求确认或代码适配 |

`cost update` 仅更新价格，不顺带更新协议和能力。明确免费或某项零费率需记录确认依据。普通 `float64` 解码零值不能充当来源价格已提供的证明。

### 6.2 生命周期

上游 missing、deprecated 或账户列表变化只产生审查提示。下架须明确范围和原因，从下一份生效快照移除该四维身份，维护源与历史保留。恢复形成新候选并重新检查。加载器不把已下架条目从内置基线补回；用户仍请求该型号时明确报错，不自动替换模型。

## 7. 代码兼容接纳与证据

正式接纳须有已确认定义和适用的受控 E2E。只验证当前选定的实际代码，不推断更早程序兼容。记录受测提交及实际源码/输入摘要、候选摘要、执行入口、场景集合、命令、退出与原件引用。

复用协议/操作的测试合约，为每个完整模型身份确认适用性并补充差异。合约应覆盖本地加载、公共查询、公共调用、请求与响应转换、用量和计价；工具、历史、推理、多模态及参数边界按声明能力覆盖。关键 wire 预期与价格边界使用独立夹具，不能完全由待测目录生成断言。缺合约、缺场景、零匹配或测试执行失败均不能算通过。

结论统一称为“代码兼容通过”。本期不调用真实模型 API，也不据此宣称厂商实测支持或通过正式发布判定。沿用 [测试 SOP](../../docs/agents/verification.md) 对普通受控、真实测量和发布证据的区别。

无需修改代码即可通过的候选，未来具备目录独立发布条件。需要修改代码才能通过的，保留候选、关联适配变更，修改后重新检查，未来随软件与目录配套全量发布；不在模型上维护最低软件版本。本期只生成/应用本地 JSON，不实现上述发布动作。

## 8. 本地 JSON 的加载流程

沿用外层 `{ "hash": "sha256:...", "catalog": { ... } }`，`catalog` 仍为 `version/models/imageModels/classifierModels`。来源、人工确认、检查和历史不加入此运行文件；内存报告也不反写文件。这里定义本地格式，不提前决定未来线上文件格式。

加载顺序：

1. 读取所选内置或外部本地文件，严格检查根结构、已知顶层字段、版本与集合形状；先保留模型原始 JSON，不对整份模型集合做 typed 解码。
2. 以原始 `catalog` 紧凑 JSON 校验外层摘要：只去除字符串外 JSON 空白，不重排属性、不改数值或转义。此过程不依赖当前模型类型，也不执行整目录语义校验。
3. 对每个条目提取身份和原始位置，再严格逐条解码；记录未知字段、类型/约束错误及能明确识别的当前程序不支持项。
4. 按四维身份找出重复组，组内所有条目均失败，不选择第一或最后一条。
5. 对成功候选复用 `ai` 的模型约束及实际协议能力依据，避免在目录组件维护第二套协议表；当前单条临时 Catalog 的 `Hash()` 可复用部分校验，但不能代替身份/路由完整性检查。
6. 仅将加载成功的条目装配为现有 `ai.Catalog`，保持源顺序和缺省语义，重新计算有效 `Catalog.Hash()`；返回有效目录和全部条目报告。
7. Host 查询报告、构造现有 Client。启动后目录及加载状态固定，不联网刷新，不在调用中重新解释文件。

### 8.1 错误作用范围

| 错误 | 处理 |
| --- | --- |
| 单模型未知字段、字段类型/取值错误、明确不支持的协议/能力 | 该条失败，其他条目继续 |
| 身份不完整或条目不是合法模型对象 | 按集合及数组位置保留失败记录和部分身份，不能冒充可按完整身份调用的模型 |
| 四维身份重复 | 冲突组全部失败，其他条目继续 |
| 整个 JSON 无法解析、顶层结构/字段错误、摘要不符 | 整份文件失败，不能通过剔除模型掩盖问题 |
| 全部模型失败 | 返回全部报告和空可用集合，Host 展示无可用模型原因 |

单模型失败不作为整个加载调用的致命错误。完整文件失败时不得静默改用其他来源；本期无网络缓存或自动内置补回。加载器必须仍能给出文件级原因；Host 是否显式改选内置目录属于装配选择。

### 8.2 内存报告与状态语义

报告保存源版本/摘要、有效摘要、成功/失败数量，以及每条记录的完整或部分身份、集合/数组位置、状态、诊断和处理建议。失败原始条目保留供诊断，不把未知字段丢弃后假装加载成功；公开查询的错误信息继续遵守既有归属与脱敏边界。

| 状态 | 原因示例 | 含义与建议 |
| --- | --- | --- |
| `loaded` | 无失败原因 | 当前程序接受了定义；不代表取得厂商实测或 Binding 授权 |
| `failed` | `unknown_field` | 当前加载器不认识字段；提示检查目录或尝试升级，不猜可解决的最低版本 |
| `failed` | `unsupported_definition` | 能明确识别当前程序不支持的协议/能力；建议升级或检查定义 |
| `failed` | `invalid_definition` | 类型、取值、硬约束或结构校验失败；保留原因，提示修复，不一律归因版本过旧 |
| `failed` | `duplicate_identity` | 身份歧义；冲突条目全部不可用，修复目录 |

现有 `ai.Catalog` 与 Lookup/ModelsOf 仅看到成功集合。Host 从独立报告发现不可用模型及原因，不要求扩展公共 Model 类型或改变其查询返回值。

运行调用的认证、限流、网络及厂商参数错误按现有结果/错误返回，不修改加载状态，不自动下架、重试、切模型、切 Provider 或回滚目录。现有错误分类不能可靠证明“必须升级”；Host 仅将升级作为适当排查建议，保留允许公开的诊断，不输出底层未脱敏原件。

### 8.3 摘要与版本的边界

| 身份 | 描述对象 | 用途 |
| --- | --- | --- |
| 上游响应/摘录摘要 | 实际参与映射的 models.dev 资料 | 维护复现，不冒充上游版本或部署提交 |
| 外层 `hash`（来源目录摘要） | 完整原始 `catalog` 的紧凑字节 | 模型解析前校验，包含旧程序不认识的字段 |
| `Catalog.Version` | 来源目录已确定的内容/合成版本 | 定位来源，加载时不因过滤另造一套人工版本 |
| `Catalog.Hash()`（有效目录摘要） | 当前程序实际接受的 typed 目录及 Version | 继续进入 Client/CallMetadata 的价格与目录快照身份 |

过滤后有效摘要可以不同于外层摘要；来源相同而程序接受集合不同也可导致有效摘要不同。不能拿过滤后 `Hash()` 校验完整输入，也不能将外层摘要冒充实际使用集合。报告同时保留两者，历史 pin 和证据以原始事实为准。

现有快照的原始紧凑摘要与外层 `sha256:f44d07c6969346f056cc46d31fccbafb68827267910801c05bb314ac0c55348d` 相同。这只证明当前生成快照兼容此校验；对重新排序、改写数字或转义的任意等价 JSON 不保证同值。生成器应确定性编码，既有 `ai.Catalog.Hash()` 算法保持不变。
