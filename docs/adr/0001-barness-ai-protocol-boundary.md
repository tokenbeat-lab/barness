# barness-ai 的协议边界与调用级租户归属

barness 同时服务本地和云端 Agent，需要一套不会依赖 Agent 生命周期、也不会把模型服务配置与租户凭据混为一体的基础能力。barness-ai 因此作为项目内可嵌入的模型协议模块，每次调用只处理一个生成轮次：统一消息、选项、协议转换、流、最终结果、错误和用量；宿主拥有认证、上下文组织、工具执行、会话与任务调度。该边界使本地程序和云端 worker 使用相同契约，并保持上层依赖基础模块的方向。

Provider 与 API 协议分别建模，模型身份包含 Provider、协议和模型标识；每次调用由可信宿主提供租户身份，经该租户的服务绑定解析版本化凭据，重试固定同一快照。本地调用也显式归属租户，核心不自动读取环境凭据，不以 Provider ID 保存可变的“当前 key”；这是相对冻结 pi-ai 凭据模型的有意改变，用于防止共享 Client、同名 binding 和并发重试串用账户。

保留冻结 pi-ai 的可观察协议行为，包括跨模型历史降级、full/simple 选项、异步错误消息和可独立等待的最终结果；Go 的并发安全、租户授权及资源限制单独形成扩展契约。原生状态的可信归属由宿主担保而非库密封：宿主鉴权并校验存储完整性后，经不可从 JSON 反序列化得到的构造入口交给库，库只核对封套来源与当前租户和绑定是否匹配。未经担保或账户不匹配的原生状态按跨模型规则降级而不是拒绝调用，并在结果元数据和观测中记录降级；已授权的同租户跨模型转换同样不因源账户不同而整体拒绝，只检查转换后仍然保留的账户专有引用。

## Consequences

- 宿主必须承担认证与按租户读取历史的责任；TenantID 字符串不构成认证，库也无法识别任意文本的原始租户。
- 同一个协议实现可以服务多个 Provider，同一个 Provider 的不同协议由不同服务绑定明确选择；失败时不自动切换 Provider、协议或 key。
- 单次生成的网络重试可以产生多次计费，RequestID 不提供去重承诺；厂商账户配额与租户资源限制分别归属。
- 调用类标识全局唯一：RequestID 及由它派生的 AttemptID 不随租户重复，由宿主保证，库无法校验；宿主注入的准入、观测可以只按它们做键。配置类标识（BindingID、CredentialID）只在租户内唯一，不同租户可以同名（维护者决定，2026-10-02，工单 17）。
- 库返回的原生续接状态需要完整保留；默认日志、错误诊断和观测不得泄露凭据、正文或原生密文。
- 库自身产出的消息在进程内即带可信来源（调用已解析的租户、账户和模型），宿主把 Result 消息直接传入下一次调用时按同模型回放；经持久化读回的消息一律不可信，必须由宿主调用 `TrustNativeState` 重新担保。可信值的字段不导出且不参与序列化，JSON 无法携带。同进程的宿主 Go 代码可以在消息间复制该值，这属于可信宿主的职责，库不防范同进程不可信代码。
- 实现不得反向依赖 Agent、Session、TUI 或特定秘密管理产品；不建立旧工作名的兼容入口或平行实现。

## Considered Options

- 独立部署推理网关：会把宿主网络协议、认证和部署生命周期纳入基础模块，无法作为本地与云端的共同最小边界；需要网关时由宿主封装。
- Provider 全局凭据或进程环境兜底：装配较少，但同一 Provider 的多租户、多账户路由及撤销语义不清晰，因此不采用。
- 拒绝含未担保原生状态的调用：最严格，但本地读回存档、宿主遗漏恢复入口时整次生成失败，而降级能保留可见内容并通过观测暴露问题。
- 库用宿主注入的密钥密封原生状态：库可自证完整性，但本地也要管理密钥，轮换后旧会话失效；首期存储完整性已由宿主负责，出现不可信中间存储时再重议。
- 按 pi 原样回放调用方提供的原生状态：兼容性最好，但云端请求可借自报签名或密文跨账户回放，不符合租户隔离。
- 完全重定义 Go 消息与流语义：可简化局部实现，但会失去已研究的 pi-ai 兼容基线；采用同步访问与附加元数据表达 Go 扩展。

范围、接口与验收要求见 [barness-ai spec](../../.scratch/barness-ai/spec.md)。此记录描述目标架构，不表示模块已经实现或完成验证。
