# 模型目录独立发布，目录纳入与逐型号实测分别记录

2026-11-01：[ADR-0058](0058-barness-catalog-maintenance-and-isolated-loading.md) 已取代本 ADR 的当前设计合同，保留 barness 维护权、Provider 独立内容版本、三类 Catalog/四维身份、授权独立和启动后固定快照。主源改为 models.dev，生效前增加受控 E2E，旧程序按模型隔离加载；线上发布、下载、缓存及五秒预算退出本期。以下完整保留 2026-10-29 的历史背景与五轮决定，不再作为本期实施指令。

Provider 频繁发布沿用既有协议的新型号，目录随程序代码发布会延迟可用性。维护者在动态目录讨论第一轮确认：barness 审核并独立发布自己的模型目录，外部来源只生成候选变更；符合已有实现能力的新型号可以先纳入可调用目录，其自身实测状态单独记录。首版仅在应用启动时检查更新一次，选定后固定目录快照，暂不支持进程中更新。

此选择以 Provider 保证既有协议向后兼容为前提。目录纳入仍需审核来源、协议、已知约束、能力和价格定义；第五轮进一步确认，当前程序尚未适配的事实不阻止目录更新和新型号发现，具体调用问题再修复代码。目录数据不代替实现；目录发现与 Binding 授权继续独立，新条目不自动扩大租户白名单。

## 权衡与影响

- 独立目录发布可使兼容新型号无需等待程序发版；代价是部分可调用条目尚无自身真实测量，必须如实表达验证状态，不能宣称已验证支持。
- 外部源可以加速发现和整理，正式目录的定义及兼容承诺仍由 barness 审核承担；Pi 的兼容证明不自动适用于 barness。
- 首版启动时选择快照，可保留 Client 构造后目录固定的行为；新目录在下一次启动才生效。

## 第二轮确认：独立组件、Provider 范围与简单版本

维护者确认需要独立目录组件。Host 安装时即带一份默认模型目录，首次启动也可以更新；由独立组件获取、缓存、校验并交给现有 Catalog 装配入口。直接构造 barness-ai Client 不隐式联网。

发布物采用完整快照，内层沿用现有 Catalog，来源、验证状态及发布元数据放在外层；这里的完整快照以 Provider 为范围。第二轮曾将 Host 更新范围限定为已配置 Provider，第三轮进一步明确维护范围覆盖全部 barness 支持的 Provider，并允许首版按 KISS 选择全量更新，见下节。

首版遵从 KISS，仅维护模型目录的内容版本及既有内容哈希，不引入此前建议的兼容代次、最低程序版本或版本协商。新的必需协议/参数行为仍属于代码适配范围，但不要求适配完成后才能收录目录。基础数据完整性和结构校验保留，未理解字段与调用能力边界按第五轮处理。

启动更新失败、超时或目录校验失败时，保留有效缓存；采用上次有效目录，没有时采用安装自带的内置基线，并明确报告采用结果。具体时间预算待后续设计，按 Provider 的失败隔离见下节。

目录数据与维护/发布工具放在同一仓库，以 Git 审核提交为来源，形成“审核提交 → 校验 → 生成不可变发布物 → 发布”的流程，再接自动化。第四轮已确定静态 HTTPS 分发与域名，具体托管配置仍未实施。

## 第三轮确认：全量维护，Provider 独立版本与回退

目录组件维护全部 barness 支持的 Provider 的型号信息。Host 端决定启动检查范围；维护者明确允许基于 KISS 进行全量更新，并指出这能让用户感知未配置 Provider 的最新型号。本轮据此选择首版启动检查全量 Provider，不再将第二轮“仅配置 OpenAI 就不得更新 Anthropic”作为首版限制；不需要通过读取凭据来发现公开目录。

各 Provider 独立维护目录内容版本、发布完整快照，失败也只回退该 Provider，其他 Provider 的成功更新可以采用。未更新到新快照的 Provider 保留其有效缓存或内置定义。选定快照完整替换同一 Provider 的旧条目，已删除的型号不从内置目录重新补回；未配置 Provider 的定义继续可被发现，不因此获得调用授权。

多份 Provider 快照装配为现有 Catalog，仅为沿用 barness-ai 的单 Catalog 装配入口；不会把 Provider 独立维护、发布或回退改成全局同步发布。合成身份由第五轮确认，不新增需要人工维护的程序兼容版本。

## 第四轮确认：同源生成与 barness.dev 静态分发

内置默认目录与在线发布物从同一份 Git 目录数据生成。在线目录独立发布，程序发版时选定一版作为安装随附基线；不继续分别手工维护 Go 目录字面量和在线数据。

目录事实以 Provider 官方文档、公告及模型 API 为依据，Pi/models.dev 用于发现变化与辅助核对。来源冲突由维护者记录判断后发布；模型 API 返回哪些事实就使用哪些事实，不假定它已提供全部价格与硬约束，也不把受账户权限或查询条件影响的列表缺失直接解释成全球停服。

首版以 HTTPS 静态文件分发，各 Provider 有最新版本入口及不可变历史文件，域名确定为 `barness.dev`。维护者说明目前只有域名、尚未配置；本决策不表示 DNS、TLS、托管或上传已经完成。本轮工作仍限于研究和设计，不执行部署。

## 第五轮确认：装配兼容、先发现后适配、固定五秒

Q15 采纳自动合成身份：组件根据各 Provider 的选定版本与内容摘要，生成现有 Catalog.Version，继续沿用 CatalogHash。合并仅发生在交给 ai.Client 的装配边界，初始化报告保留每 Provider 的来源清单；不新增另一套人工维护的全局目录版本。

Q16 采纳维护者的修订：新版目录即使包含当前程序尚未实现的新型号、协议或参数，也应继续更新，让旧程序感知新型号；不因未适配而拒绝整家新版或回退。未知新增字段随原始快照保留，已有基础字段继续供发现使用；仍保留基本格式、归属、完整性与已知值的有效性校验，损坏数据不等于未适配数据。调用该型号时，程序可报告未实现协议/参数或 Provider 真实错误，之后再适配代码；不会据此自动切换型号、Provider 或回滚整个目录。

这要求首次接入动态目录时梳理 Client 构造校验：程序能力与固定首批型号范围不能使其他有效定义一起无法发现；相关约束移到对应型号调用阶段，仍须遵守已有授权、已知硬约束和错误归属。新目录不承诺当前版本已经能成功执行每个已收录型号，也不保证未知计费语义能被正确估算，不能把缺失费率填成零。

Q17 确认全量启动检查固定五秒总预算，首版不给 Host 配置调整入口。已完成的 Provider 更新可以采用，超时未完成项按缓存/内置规则回退；下次启动再检查，无后台重试。正常的调用方取消继续生效。

## 与既有决策的关系

针对未来动态目录，本决策修订 [ADR-0018](0018-barness-ai-catalog-inclusion-criterion.md) 将全部硬约束已实现及自身验收作为目录纳入前提的要求；目录收录、当前程序适配与自身实测分别记录。保留调用中硬约束与可选特性的区分，已知硬约束不能绕过，新增能力不因目录审核自动成为已适配/已验证支持。自身测量、支持矩阵、历史证据和发布判定继续按各自事实记录，不重写为新的通过结论。

[ADR-0054](0054-barness-ai-xai-responses.md)、[ADR-0056](0056-barness-ai-xai-images.md) 及 Kimi 等首期合同中的固定型号边界，需要在后续设计中区分实现约束与已验收范围，再按本决策评审迁移。本 ADR 不直接放宽当前运行时校验，也不宣称新型号已经可以由现有程序使用。

维护者于 2026-10-29 确认“理解准确，可以定稿”，Q1–Q17 及整体设计共识成立，研究与讨论完成，产品尚未实施。静态托管的供应商、DNS/TLS 与上传权限留待部署工作具体配置。来源与决策记录见[研究报告](../../.scratch/barness-ai-dynamic-catalog/research.md)、[讨论记录](../../.scratch/barness-ai-dynamic-catalog/discussion.md)及[定稿设计](../../.scratch/barness-ai-dynamic-catalog/design.md)。
